# Database and PL/pgSQL Standards

## Platform

BrickSetu uses PostgreSQL 16+ and PL/pgSQL. PostgreSQL is the authoritative source for business data, stock, payment balances, and posted calculations. Node.js accesses it through parameterized queries and versioned SQL migrations.

## Database ownership

Use PostgreSQL schemas to make ownership visible:

| Schema | Responsibility |
| --- | --- |
| `core` | Business unit, controlled lookups, common reference data. |
| `auth` | Administrator identities and sessions. |
| `workers` | Workers and rate history. |
| `production` | Batches, daily work, and production stages. |
| `inventory` | Brick stock lots, movement ledger, and adjustments. |
| `materials` | Materials, purchases, lots, and consumption. |
| `parties` | Customers and suppliers. |
| `sales` | Sales records and finished-stock allocations. |
| `finance` | Payments, expenses, worker settlements, and allocations. |
| `transport` | Vehicles and trips. |
| `audit` | Immutable event log. |
| `reporting` | Read-only views or functions used by reports. |

Database ownership follows feature ownership, not a generic technical layer. Cross-schema foreign keys are allowed when they model a real domain relationship.

## Data rules

- Use `uuid` primary keys generated by PostgreSQL.
- Use `timestamptz` for audit/event timestamps and `date` for business dates. Interpret business dates in `Asia/Kolkata`.
- Store brick counts as non-negative integers. Store material quantities as `numeric(14,3)` with an explicit unit.
- Store money as `bigint` paise; never use floating-point values for rates, balances, or totals.
- Add `created_at`, `created_by`, `updated_at`, and `updated_by` to editable records. Posted ledgers also require a business date, status, and immutable source reference.
- Archive inactive master data with `archived_at`; do not hard-delete records that are referenced by transactions.
- Use explicit `CHECK`, foreign-key, unique, and non-negative constraints. Application validation complements but never replaces database constraints.

## Migrations

- Store ordered, append-only SQL files in `backend/db/migrations/` using `NNNN_short_description.sql`.
- Each migration records schema, functions, indexes, and any safe data transition needed for that change.
- Migrations run once and are recorded in a migration ledger. Never edit an already-applied migration; add a new migration.
- Production migrations must be backward-compatible where possible. Do not use destructive down-migrations as an operational recovery strategy.
- Run migrations in a transaction when PostgreSQL permits it and test them against a clean database and an upgraded database.

## PL/pgSQL rules

- Put function source beside migrations under `backend/db/functions/<owner-feature>/` and create/replace it through a migration.
- Use functions for posting stock movements, material consumption, batch-stage transitions, payment allocation, settlement generation/voiding, and other integrity-critical workflows.
- Function names must describe the business action, for example `inventory.post_adjustment` or `finance.allocate_payment`.
- A function validates its preconditions, locks the affected rows with `FOR UPDATE` when needed, writes every related record, and either completes entirely or raises an error.
- Default to `SECURITY INVOKER`. Any `SECURITY DEFINER` function requires explicit review, fixed `search_path`, and restricted execute privileges.
- Keep triggers mechanical and visible: audit capture, timestamps, and narrowly defined derived fields. Do not hide complex business workflows in triggers.
- All business-write functions must create an `audit.event` record containing the actor, action, source record, timestamp, and before/after metadata appropriate to the action.

## Financial and stock integrity

- Stock is derived from an immutable movement ledger; cached balances, if later added, are projections and must be rebuildable.
- A payment's remaining amount is derived from its allocations. Customer, supplier, and worker balances are derived from posted charges and payments.
- Material and finished-brick lots use FIFO allocation. A transaction cannot consume more than its available quantity.
- A posted transaction may be voided only through its owning workflow. The void creates compensating ledger entries and preserves history.
